# 十五、会话管理

## 1、模块概述

`SessionManager` 是 CountBot 中管理会话生命周期和消息持久化的核心组件，位于 `backend/modules/session/manager.py`。它负责：

- 会话的 CRUD 操作（创建、查询、更新、删除）
- 消息的添加与分页查询
- **短期记忆优化**：通过对话总结器压缩历史上下文
- **溢出总结**：将超出滑动窗口的旧消息自动总结到长期记忆

### （1）在架构中的位置

```
用户消息
    │
    ▼
┌──────────────────────────────────────────────┐
│  接入层：Chat API / WebSocket / Channel      │
│  ┌────────────────────────────┐              │
│  │     SessionManager         │ ← 本文重点   │
│  │  ┌──────┐  ┌───────────┐  │              │
│  │  │Session│  │  Message   │  │              │
│  │  └──────┘  └───────────┘  │              │
│  └──────────┬─────────────────┘              │
│             │                                 │
│     ┌───────┴────────┐                        │
│     ▼                ▼                        │
│  AgentLoop      MemoryStore                   │
│「处理消息」    「长期记忆写入」                 │
└──────────────────────────────────────────────┘
```

SessionManager 是接入层和 Agent 核心之间的桥梁：
- **向上**：为 Chat API、WebSocket、Cron 提供会话和消息的读写接口
- **向下**：为 AgentLoop 准备历史上下文，将溢出消息写入 MemoryStore

### （2）数据模型

SessionManager 操作两张表：

**Session 表**（`backend/models/session.py`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String（主键） | UUID 字符串 |
| `name` | String | 会话名称 |
| `created_at` | DateTime | 创建时间 |
| `updated_at` | DateTime | 最后更新时间 |
| `summary` | String(200) | 会话摘要（20-200 字） |
| `summary_updated_at` | DateTime | 摘要更新时间 |
| `last_summarized_msg_id` | Integer | 溢出总结的水位线（见第 4 节） |
| `messages` | relationship | 一对多关联 Message，级联删除 |

**Message 表**（`backend/models/message.py`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | Integer（主键） | 自增 ID |
| `session_id` | String（外键） | 关联 Session.id |
| `role` | String | `user` / `assistant` / `system` |
| `content` | Text | 消息内容 |
| `created_at` | DateTime | 创建时间 |

复合索引：`(session_id, created_at)` — 加速按会话查询消息。

## 2、SessionManager 的创建与注入

SessionManager 在三个地方被创建，各自的 summarizer 配置不同：

```
┌─────────────────────────────────────────────────────┐
│                   创建场景对比                        │
├─────────────┬──────────────┬────────────────────────┤
│   场景       │  有 summarizer │  说明                 │
├─────────────┼──────────────┼────────────────────────┤
│ Chat API    │  ✅ 有        │ 需要上下文压缩          │
│ WebSocket   │  ❌ 无        │ 仅做基本的消息读写      │
│ Cron 任务   │  ❌ 无        │ 后台任务，不需要总结     │
└─────────────┴──────────────┴────────────────────────┘
```

### （1）Chat API 中的创建

```python
# backend/api/chat.py:176-180
from backend.modules.agent.memory import ConversationSummarizer

summarizer = ConversationSummarizer(provider=provider, char_limit=2000)
session_manager = SessionManager(db, summarizer=summarizer)
```

Chat API 是唯一注入了 `summarizer` 的场景，因为 HTTP 接口走的是 SSE 流式推送，需要在发送消息前压缩历史上下文。

### （2）WebSocket 中的创建

```python
# backend/ws/events.py:76
session_manager = SessionManager(db)
```

WebSocket 场景不传 summarizer。WebSocket 处理器直接用 `get_messages(limit=50)` 截取最近 50 条消息作为上下文，没有使用总结压缩机制。

### （3）Cron 任务中的创建

```python
# backend/app.py:312
session_manager = SessionManager(shared["workspace"])
```

Cron 场景传入的是 workspace 路径而非 db session，用于定时任务执行时的消息管理。

## 3、核心方法详解

### （1）会话 CRUD

这部分比较直接，都是标准的 SQLAlchemy 异步操作：

| 方法 | 功能 | 调用方 |
|------|------|--------|
| `create_session(name)` | 创建新会话，生成 UUID | Chat API: POST /sessions |
| `get_session(session_id)` | 按 ID 查询单个会话 | 多处验证会话存在性 |
| `list_sessions(limit, offset)` | 列出会话，按 updated_at 降序 | Chat API: GET /sessions |
| `update_session(session_id, name)` | 更新会话名称 | Chat API: PUT /sessions/{id} |
| `delete_session(session_id)` | 删除会话（级联删除消息） | Chat API: DELETE /sessions/{id} |

### （2）消息管理

#### add_message

```python
async def add_message(self, session_id, role, content) -> Message:
```

- 校验 role 必须是 `user` / `assistant` / `system`
- 创建 Message 记录
- **同时更新 session.updated_at**（这样列表排序就能反映最近活跃的会话）
- 调用方：Chat API 和 WebSocket 在保存用户消息和助手回复时各调一次

#### get_messages 的分页策略

```python
async def get_messages(self, session_id, limit=None, offset=0) -> list[Message]:
```

这里有一个值得注意的设计：

```
场景：limit=20，共 100 条消息

普通分页思路：按 ASC 排序取前 20 → 拿到的是最旧的 20 条 ❌
本方法的做法：先按 DESC 取 20 条（最新的），再 reverse → 最新的 20 条，且保持时间正序 ✅
```

为什么这样做？因为给 LLM 的上下文需要的是**最近的对话**，而不是最早的。

### （3）get_history_with_summary — 短期记忆压缩

这是 SessionManager 中最核心的方法，负责将冗长的历史对话压缩为可用的 LLM 上下文：

```
原始历史（50 条消息）
    │
    ▼  len(messages) > 15 且 summarizer 存在？
    │
    ├── 否 → 直接返回全部消息的 dict 列表
    │
    └── 是 → should_summarize() 检查字符数是否超限
         │
         ├── 否 → 直接返回
         │
         └── 是 →
              │
              ▼  get_messages_to_keep(keep_recent=10)
              ┌────────────────────────────────────┐
              │ 前 40 条 → to_summarize（被总结）    │
              │ 后 10 条 → to_keep（保留原文）       │
              └────────────────────────────────────┘
              │
              ▼  summarize_conversation()
              │
              ▼  返回结果：
              ┌────────────────────────────────────┐
              │ [0] system: "## Previous Summary"   │
              │ [1] 第 41 条消息                     │
              │ ...                                  │
              │ [10] 第 50 条消息                    │
              └────────────────────────────────────┘
```

关键点：
- **阈值**：消息数 ≤ 15 时不触发总结，直接返回原文
- **保留最近 10 条**：确保 LLM 能看到最近的完整对话
- **总结作为 system 消息**：注入到消息列表头部
- **conversation_summary 是实例变量**：在同一个请求周期内累积，支持递归总结

### （4）summarize_overflow — 滚动窗口溢出总结

这是另一个重要机制，用于防止长对话中的信息丢失。当配置了 `max_history`（最大保留消息数）时，超出部分的旧消息会在被截断前先总结到 MEMORY.md。

```
消息时间线：
msg_1  msg_2  ...  msg_70  msg_71  ...  msg_100
│──── 溢出区域 ────│────── 保留区域 ──────│
     （被截断）           （max_history=30）

没有 summarize_overflow：
  msg_1 ~ msg_70 直接丢失 ❌

有 summarize_overflow：
  msg_1 ~ msg_70 → LLM 总结 → 写入 MEMORY.md ✅
  然后 msg_71 ~ msg_100 作为上下文发送给 LLM
```

#### 水位线机制：`last_summarized_msg_id`

为了避免重复总结，Session 表有一个 `last_summarized_msg_id` 字段作为**水位线**：

```
第一次调用 summarize_overflow:
  last_summarized_msg_id = 0
  溢出消息: id 1~70 → 总结 → 写入记忆
  更新: last_summarized_msg_id = 70

第二次调用（新增了 20 条消息）:
  last_summarized_msg_id = 70
  查询: id > 70 的溢出消息 → 只有新溢出的部分
  避免了重复总结 id 1~70
```

#### 完整执行流程

```python
# backend/api/chat.py:404-417 — 在加载历史之前调用
if max_history > 0:
    await session_manager.summarize_overflow(
        session_id=request.session_id,
        max_history=max_history,
        provider=agent_loop.provider,
        model=agent_loop.model,
        memory_store=_overflow_memory,
    )
```

内部步骤：
1. 查总消息数，判断是否有溢出
2. 读取 `last_summarized_msg_id`，查询**尚未总结的溢出消息**
3. 过滤：只总结 user/assistant 消息，跳过 system
4. 如果不足 3 条，不值得总结，只更新水位线
5. 用 `MessageAnalyzer.format_messages_for_summary()` 格式化
6. 用 `OVERFLOW_SUMMARY_PROMPT` + LLM 生成总结
7. 如果总结有效（不含「无需记录」），写入 `MemoryStore.append_entry(source="auto-overflow")`
8. 更新 `last_summarized_msg_id`

## 4、三种记忆总结机制对比

CountBot 中有三种不同的对话总结机制，容易混淆：

| 机制                           | 触发时机                  | 写入位置      | 目的            |
| ---------------------------- | --------------------- | --------- | ------------- |
| **get_history_with_summary** | 每次发送消息时               | 内存（注入上下文） | 压缩当次请求的历史上下文  |
| **summarize_overflow**       | 每次发送消息前               | MEMORY.md | 防止滑动窗口截断时信息丢失 |
| **_maybe_auto_summarize**    | 消息数 ≥ 30 或字符数 ≥ 15000 | MEMORY.md | 长对话自动存档重要信息   |

三者的关系：

```
用户发送消息
    │
    ▼
① summarize_overflow()       ← 先处理溢出，写入 MEMORY.md
    │
    ▼
② get_history_with_summary() ← 加载上下文（可能带总结压缩）
    │
    ▼
   AgentLoop.process_message() → 流式响应
    │
    ▼
③ _maybe_auto_summarize()    ← 响应完成后，检查是否需要自动存档
```

## 5、消息流转全景图

以 Chat API 发送消息为例，展示 SessionManager 在整个流程中的参与：

```
POST /api/chat/send  { session_id, message }
    │
    ▼
SessionManager.add_message(role="user")     ← ① 保存用户消息
    │
    ▼
SessionManager.summarize_overflow()          ← ② 溢出总结（如有）
    │
    ▼
SessionManager.get_history_with_summary()    ← ③ 加载历史上下文
    │                                              「返回 list[dict]」
    ▼
AgentLoop.process_message(context=...)       ← ④ Agent 处理
    │                                              「流式输出」
    ▼
SessionManager.add_message(role="assistant") ← ⑤ 保存助手回复
    │
    ▼
_maybe_auto_summarize()                      ← ⑥ 自动存档检查
```

WebSocket 的流程类似，但步骤 ②③ 简化为直接 `get_messages(limit=50)`。

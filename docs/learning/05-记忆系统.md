# 五、记忆系统

记忆系统让 AI 能够跨会话记住重要信息，是 CountBot 从 Chatbot 进化为 Agent 的关键能力之一。

核心文件：`backend/modules/agent/memory.py`

## 1、记忆系统概览

记忆系统包含两个核心组件：

| 组件                       | 职责             |     |
| ------------------------ | -------------- | --- |
| `MemoryStore`            | 记忆的存储、搜索、读取、删除 |     |
| `ConversationSummarizer` | 对话历史的自动总结和压缩   |     |

```
记忆系统
├── MemoryStore（持久化记忆）
│   ├── append_entry()  → 写入记忆
│   ├── search()        → 关键词搜索
│   ├── read_lines()    → 按行号读取
│   └── delete_lines()  → 按行号删除
│
└── ConversationSummarizer（对话总结）
    ├── should_summarize()        → 判断是否需要总结
    └── summarize_conversation()  → 调用 LLM 生成总结
```

## 2、记忆存储格式

### （1）文件位置

记忆存储在工作区的 `memory/MEMORY.md` 文件中：

```
workspace/
├── memory/
│   └── MEMORY.md    ← 所有记忆都在这个文件里
```

### （2）行式文本格式

每条记忆占一行，格式为：

```
日期|来源|内容事项1；事项2；事项3
```

实际示例：
```
2026-02-15|web-chat|用户询问天气API方案；决定使用OpenWeatherMap；缓存策略选Redis TTL=3600s
2026-02-15|telegram|用户要求每天早上9点发送日报；已创建cron任务
2026-02-16|dingtalk|用户偏好Python而非Java；常用Flask框架
```

### （3）为什么用文本文件而不是数据库？

这是一个有意的设计决策：

| 优势        | 说明                           |
| --------- | ---------------------------- |
| **可读性**   | 用户可以直接打开 MEMORY.md 查看和手动编辑记忆 |
| **简单性**   | 不需要额外的查询语言，行式格式天然支持追加操作      |
| **AI 友好** | 记忆内容可以直接作为文本嵌入到 LLM 提示词中     |
| **可移植性**  | 一个文件即可迁移所有记忆                 |

代价是搜索性能——关键词搜索需要遍历全文。但对于个人助手场景，记忆量通常不大，线性搜索完全够用。

## 3、写入记忆

### （1）append_entry 方法

```python
# memory.py:59-84
def append_entry(self, source, content):
    date_str = datetime.now().strftime("%Y-%m-%d")
    # 清理换行符，保持行式格式
    content = content.replace('\n', ' ').replace('\r', ' ')
    content = ' '.join(content.split())  # 压缩空格
    entry = f"{date_str}|{source}|{content}"

    lines = self._read_lines()
    lines.append(entry)
    self._write_lines(lines)
    return len(lines)  # 返回行号
```

### （2）关键细节

- **换行符清理**：必须将内容中的换行符替换为空格，否则会破坏行式格式
- **空格压缩**：多个连续空格压缩为一个，保持整洁
- **来源标记**：`source` 参数记录记忆来自哪个渠道（web-chat、telegram 等）
- **返回行号**：返回新条目的行号，方便后续引用

### （3）触发时机

记忆写入由 AI 主动调用 `memory_write` 工具触发。在系统提示词中会指导 AI：
- 记住用户明确表达的偏好（如"我喜欢 Python"）
- 记住重要的决策（如"我们决定使用 Redis"）
- 记住用户的个人信息（如"我的生日是..."）

## 4、关键词搜索

### （1）search 方法

```python
# memory.py:115-165
def search(self, keywords, max_results=15, match_mode="or"):
    lines = self._read_lines()
    keywords = [kw.strip().lower() for kw in keywords if kw.strip()]

    results = []
    for i, line in enumerate(lines):
        line_lower = line.lower()
        if match_mode == "and":
            if all(kw in line_lower for kw in keywords):  # AND 逻辑
                results.append(f"[{i + 1}] {line}")
        else:
            if any(kw in line_lower for kw in keywords):  # OR 逻辑
                results.append(f"[{i + 1}] {line}")
    return "\n".join(results[:max_results])
```

### （2）两种搜索模式

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| **OR**（默认）| 任意关键词匹配即返回 | 模糊搜索，如搜索"天气 API" |
| **AND** | 所有关键词都必须匹配 | 精确搜索，如搜索"Redis 缓存" |

### （3）搜索特点

- **大小写不敏感**：关键词和记忆内容都转小写后比较
- **子串匹配**：使用 Python 的 `in` 运算符，支持部分匹配
- **结果带行号**：返回格式为 `[行号] 记忆内容`，方便后续按行号操作
- **结果限制**：默认最多返回 15 条，避免返回过多内容占用 LLM 上下文

## 6、ConversationSummarizer（对话总结器）

### （1）作用

当对话历史过长时，总结器会将历史消息压缩为一段摘要，放入系统提示词的 `## Current Session Context` 中。这样既保留了关键信息，又不会超出 LLM 的上下文窗口限制。

### （2）核心方法


```python

    # 当消息超过阈值时触发总结
```

总结在以下任一条件满足时触发：
- 消息数量超过 **20 条**
- 消息总字符数超过 **10000 字符**

### （4）递归总结

如果已经有了之前的总结（`previous_summary` 不为空），会使用**递归总结**策略：将旧总结和新消息一起发给 LLM，生成更新后的总结。这样可以不断累积对话上下文，而不会丢失早期信息。

### （5）总结提示词

总结使用 `agent/prompts.py` 中的 `CONVERSATION_TO_MEMORY_PROMPT` 模板，指导 LLM 提取关键信息：
- 用户的偏好和决策
- 讨论的重要技术方案
- 未完成的任务
- 用户的个人信息

## 7、历史消息的三层压缩机制

LLM 的上下文窗口是有限的，一个 Session 的消息不可能全部塞给 LLM。CountBot 通过三层机制来控制发送给 LLM 的历史消息量：

```
用户发送新消息
    │
    ├── 第一层：滚动窗口溢出总结（发消息前执行）
    │   检查消息总数是否超过 max_history
    │   超出的旧消息 → LLM 总结 → 写入 MEMORY.md → 只保留最近 N 条
    │
    ├── 第二层：对话内总结压缩（加载历史时执行）
    │   保留的消息是否超过 20 条或 10000 字符
    │   超出的旧消息 → LLM 生成 summary → [summary] + [最近 10 条原文] 送给 LLM
    │
    └── 第三层：自动记忆写入（回复完成后执行）
        消息数 >= 30 或总字符 >= 15000
        整个对话 → LLM 总结 → 写入 MEMORY.md 长期记忆
```

### （1）第一层：滚动窗口溢出总结

核心代码：`session/manager.py` 的 `summarize_overflow()` 方法

当 `max_history` 配置生效时（比如配成 50），每次发消息前先检查消息总数。超出窗口的旧消息会被 LLM 总结后写入 `MEMORY.md`：

```
假设 session 有 80 条消息，max_history = 50

旧消息 (30条)              最近消息 (50条)
├─ msg 1                   ├─ msg 51
├─ msg 2                   ├─ msg 52
├─ ...                     ├─ ...
└─ msg 30                  └─ msg 80
     │                          │
     ↓                          ↓
LLM 总结 → 写入 MEMORY.md    保留，送给 LLM 当上下文
```

通过 `Session.last_summarized_msg_id` 字段跟踪已经总结到哪条消息，避免重复总结。

> **Java 类比**：类似 `RingBuffer` 溢出时把旧数据持久化到磁盘。

### （2）第二层：对话内总结压缩

核心代码：`session/manager.py` 的 `get_history_with_summary()` 方法

即使截断到 50 条，消息量还是可能很大。加载历史时会检查是否需要进一步压缩：

```
50 条消息，超过 20 条阈值

旧消息 (40条)              最近消息 (10条)
├─ msg 11                  ├─ msg 41
├─ msg 12                  ├─ msg 42
├─ ...                     ├─ ...
└─ msg 40                  └─ msg 50
     │                          │
     ↓                          ↓
LLM 生成 summary           原样保留
     │
     ↓
拼成：[summary 系统消息] + [最近 10 条原始消息]  → 送给 LLM
```

这就是上面第 6 节 `ConversationSummarizer` 的应用场景。压缩后的 summary 以 `role: "system"` 的形式插入消息列表开头，LLM 能看到之前的对话要点但不占用太多 token。

> **Java 类比**：类似 `@Cacheable` 把热数据压缩后放进缓存。

### （3）第三层：自动记忆写入

核心代码：`api/chat.py` 的 `_maybe_auto_summarize()` 函数

AI 回复完成后，系统检查当前会话是否达到自动总结阈值。满足条件时，将整个对话总结写入 `MEMORY.md` 长期记忆：

- 消息数 >= 30 条，或总字符 >= 15000
- 距上次自动总结后新增了至少 30 条消息（避免频繁触发）

> **Java 类比**：类似定时 checkpoint 机制，确保有价值的对话信息不会因为会话关闭而丢失。

### （4）三层机制对比

| 层级     | 触发时机  | 触发条件                   | 做什么                       | 代码位置                                            |
| ------ | ----- | ---------------------- | ------------------------- | ----------------------------------------------- |
| 滚动窗口溢出 | 发消息前  | 消息数 > max_history      | 溢出部分总结 → 写入 MEMORY.md     | `session/manager.py:summarize_overflow()`       |
| 对话内压缩  | 加载历史时 | 消息 > 20 条 或 > 10000 字符 | 旧消息 → summary + 最近 10 条原文 | `session/manager.py:get_history_with_summary()` |
| 自动记忆写入 | 回复完成后 | 消息 >= 30 或 字符 >= 15000 | 整个对话总结 → 写入 MEMORY.md     | `api/chat.py:_maybe_auto_summarize()`           |

三层各有分工：第一层控制"送给 LLM 多少条原始消息"，第二层控制"这些消息怎么压缩后送出去"，第三层确保"有价值的信息写入长期记忆不丢失"。

## 8、记忆工具与记忆系统的关系

记忆系统通过三个工具暴露给 AI：

```
memory_write  → MemoryStore.append_entry()
memory_search → MemoryStore.search()
memory_read   → MemoryStore.read_lines()
```

AI 在对话中根据系统提示词的指导，主动调用这些工具来管理记忆。例如：
- 用户说"我喜欢用 Flask" → AI 调用 `memory_write` 记录偏好
- 用户问"我之前说过用什么框架" → AI 调用 `memory_search` 搜索"框架"
- AI 需要回顾最近的记忆 → 调用 `memory_read` 读取最近几行

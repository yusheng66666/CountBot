# 六、子代理系统

子代理系统让主 Agent 能够将复杂、耗时的任务"委派"给后台运行的独立 Agent，类似于"主管把任务分配给下属"。

核心文件：
- `backend/modules/agent/subagent.py` — SubagentManager 和 SubagentTask
- `backend/modules/tools/spawn.py` — SpawnTool（主 Agent 创建子代理的入口）
- `backend/ws/task_notifications.py` — WebSocket 任务通知推送
- `backend/api/tasks.py` — 任务查询/取消的 HTTP API

## 1、为什么需要子代理？

主 Agent 通过 WebSocket 与前端交互，是同步阻塞的——用户发一条消息，必须等 Agent 处理完才能继续。如果遇到耗时任务（如分析整个项目代码、批量处理文件），用户就要一直等着。

子代理解决的问题：

```
没有子代理：
用户: "分析一下整个项目的代码结构"
  ↓
主 Agent 开始分析（可能需要几分钟）
  ↓
用户一直等待...
  ↓
分析完成，返回结果

有子代理：
用户: "分析一下整个项目的代码结构"
  ↓
主 Agent: "已启动后台任务，分析中..."（立即返回）
  ↓
用户可以继续聊天
  ↓
后台子代理独立运行，完成后通知前端
```

## 2、三个核心类

### （1）TaskStatus — 任务状态

```python
class TaskStatus(Enum):
    PENDING = "pending"        # 已创建，等待执行
    RUNNING = "running"        # 正在运行
    COMPLETED = "completed"    # 执行完成
    FAILED = "failed"          # 执行失败
    CANCELLED = "cancelled"    # 被用户取消
```

状态流转：

```
PENDING → RUNNING → COMPLETED
                  → FAILED
                  → CANCELLED
```

### （2）SubagentTask — 任务对象

存储单个任务的全部信息：

```python
class SubagentTask:
    task_id: str              # 唯一标识（UUID）
    label: str                # 显示标签，如 "代码分析"
    message: str              # 任务描述（发给子代理的指令）
    session_id: str | None    # 关联的聊天会话 ID
    status: TaskStatus        # 当前状态
    progress: int             # 进度 0-100
    result: str | None        # 执行结果（完成后才有）
    error: str | None         # 错误信息（失败时才有）
    created_at: datetime      # 创建时间
    started_at: datetime      # 开始执行时间
    completed_at: datetime    # 完成时间
```

### （3）SubagentManager — 管理器

管理所有子代理任务的生命周期：

```python
class SubagentManager:
    def __init__(self, provider, workspace, model, temperature, max_tokens):
        self.tasks: dict[str, SubagentTask] = {}           # 所有任务（task_id → Task）
        self.running_tasks: dict[str, asyncio.Task] = {}   # 运行中的异步任务
```

## 3、完整执行流程

### （1）从用户消息到子代理启动

```
用户发送消息: "分析 backend/modules 目录的代码结构"
    │
    ▼
AgentLoop.process_message()
    │
    ├─ 调用 LLM，LLM 判断这是耗时任务
    ├─ LLM 决定调用 spawn 工具
    │
    ▼
SpawnTool.execute(task="分析 backend/modules...", label="代码结构分析")
    │
    ├─ manager.create_task(label, message, session_id)
    │     └─ 生成 UUID，创建 SubagentTask，存入 self.tasks
    │
    ├─ await manager.execute_task(task_id)
    │     ├─ notify_task_created(task_id, label)  ← WebSocket 广播"任务已创建"
    │     └─ asyncio.create_task(self._run_task(task))  ← 后台异步启动
    │
    └─ 返回: "子 Agent [代码结构分析] 已启动 (ID: xxx)"
          │
          ▼
    主 Agent 将这个返回值告诉用户，然后继续处理其他消息
```

### （2）子代理后台执行

`_run_task()` 是子代理的核心——它在后台运行一个独立的 Agent Loop：

```python
async def _run_task(self, task: SubagentTask) -> None:
    # 1. 构建子代理专用的系统提示词
    system_prompt = self._build_subagent_prompt(task.message)

    # 2. 构建消息列表（只有系统提示词和任务描述，没有历史对话）
    messages = [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": task.message},
    ]

    # 3. 创建独立的工具集（比主 Agent 少）
    tools = ToolRegistry()
    tools.register(ReadFileTool(self.workspace))
    tools.register(WriteFileTool(self.workspace))
    tools.register(EditFileTool(self.workspace))
    tools.register(ListDirTool(self.workspace))
    tools.register(ExecTool(workspace=self.workspace, timeout=300))
    # 注意：没有 SpawnTool（防止递归创建子代理）

    # 4. ReAct 循环（最多 15 次迭代）
    iteration = 0
    while iteration < 15:
        iteration += 1

        # 调用 LLM
        async for chunk in self.provider.chat_stream(messages=messages, tools=...):
            # 收集文本响应和工具调用

        # 有工具调用 → 执行工具，将结果加入 messages，继续循环
        # 没有工具调用 → LLM 认为任务完成，退出循环

        task.progress = min(90, task.progress + 5)
        notify_task_progress(task.task_id, task.progress)  # ← WebSocket 推送进度

    # 5. 完成
    task.result = "..."
    task.status = TaskStatus.COMPLETED
    task.progress = 100
    notify_task_complete(task.task_id, task.result)    # ← WebSocket 推送"完成"
    await self._deliver_result_to_session(task)        # ← 实时投递结果到聊天界面
```

### （3）异常处理与通知

`_run_task()` 的 try/except 结构覆盖了三种结束状态：

```
正常完成 → COMPLETED → notify_task_complete → _deliver_result_to_session
被取消   → CANCELLED → notify_task_failed("任务已取消") → _deliver_result_to_session
出异常   → FAILED    → notify_task_failed(error) → _deliver_result_to_session
```

无论哪种结果，`finally` 块都会从 `running_tasks` 中清理掉对应的 asyncio.Task。

## 4、子代理 vs 主 Agent

### （1）能力对比

| 维度 | 主 Agent | 子代理 |
|------|----------|--------|
| 最大迭代次数 | 25 | 15 |
| 可用工具 | 全部（含 spawn、memory 等） | 受限（仅文件、shell、web） |
| Shell 超时 | 30s（默认） | 300s（更长，适合编译等任务） |
| 系统提示词 | 完整的 Persona（名字、性格等） | 简洁的任务专用提示词 |
| 消息历史 | 完整对话历史 | 仅当前任务描述 |
| 能否创建子代理 | 可以 | 不可以（防止递归） |
| 执行方式 | 同步（用户等待） | 异步（后台运行） |
| 能否直接回复用户 | 可以 | 不可以（结果由主 Agent 转达） |

### （2）为什么子代理的工具更少？

**安全考虑**：
- 没有 `spawn` 工具 → 防止子代理无限创建子代理（递归炸弹）
- 没有 `memory_write` → 子代理不应该修改 AI 的长期记忆
- `allow_dangerous=False` → 禁止危险命令

**职责单一**：
- 子代理只负责完成特定任务，不需要聊天、记忆等社交能力
- 工具越少，出错的可能性越小

### （3）为什么子代理的 Shell 超时更长？

主 Agent 的 Shell 默认 30 秒超时，因为用户在等待，不能卡太久。子代理在后台运行，没人等它，所以超时设为 300 秒（5 分钟），适合编译项目、运行测试等耗时操作。

## 5、子代理的系统提示词

主 Agent 的提示词包含丰富的 Persona 配置（AI 名字、性格、记忆等），子代理的提示词则非常简洁直接：

```python
def _build_subagent_prompt(self, task: str) -> str:
    return f"""# 子代理 (Subagent)

你是主代理创建的子代理，专门负责完成特定任务。

## 你的任务
{task}

## 工作规则
1. 专注任务: 只完成分配的任务，不做其他事情
2. 简洁高效: 最终响应会报告给主代理，保持简洁但信息完整
3. 不要闲聊: 不要发起对话或承担额外任务
4. 彻底完成: 确保任务完整完成，提供清晰的结果总结

## 限制
- 不能直接向用户发送消息
- 不能创建其他子代理
- 无法访问主代理的对话历史

## 工作空间
{workspace_path}

## 完成标准
任务完成后，提供清晰的总结：
- 完成了什么
- 发现了什么（如果是调查任务）
- 遇到的问题（如果有）
- 建议的后续步骤（如果需要）"""
```

关键设计：
- 明确身份"你是子代理"→ 避免 LLM 试图和用户聊天
- 强调"只完成分配的任务"→ 防止 LLM 发散
- 列出限制 → 让 LLM 知道自己的边界

## 6、SpawnTool — 主 Agent 的入口

SpawnTool 是主 Agent 用来创建子代理的工具，定义在 `backend/modules/tools/spawn.py`：

```python
class SpawnTool(Tool):
    @property
    def name(self) -> str:
        return "spawn"

    @property
    def parameters(self) -> dict:
        return {
            "type": "object",
            "properties": {
                "task": {
                    "type": "string",
                    "description": "Task description for the background agent",
                },
                "label": {
                    "type": "string",
                    "description": "Short label for task display (optional)",
                },
            },
            "required": ["task"],
        }

    async def execute(self, task: str, label: str | None = None, **kwargs) -> str:
        # 创建任务
        task_id = self._manager.create_task(
            label=label or task[:30] + "...",
            message=task,
            session_id=self._session_id,
        )
        # 异步执行（后台运行，不等待完成）
        await self._manager.execute_task(task_id)
        return f"子 Agent [{label}] 已启动 (ID: {task_id})"
```

注意 `execute_task()` 内部用的是 `asyncio.create_task()`，这意味着任务在后台运行，`execute()` 方法立即返回。主 Agent 拿到返回的字符串后告诉用户"任务已启动"。

## 7、任务管理 API

前端可以通过 HTTP API 查询和管理子代理任务：

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/tasks` | GET | 列出所有任务（支持 status、session_id 过滤） |
| `/api/tasks/{task_id}` | GET | 获取单个任务详情 |
| `/api/tasks/stats` | GET | 获取任务统计（各状态数量） |
| `/api/tasks/{task_id}` | DELETE | 取消运行中的任务 |
| `/api/tasks/{task_id}/delete` | POST | 删除已完成的任务记录 |

## 9、结果投递机制

子代理在后台独立运行，完成后需要把结果"送"回给用户。这涉及两个问题：实时通知和持久化。

### （1）通知基础设施

`backend/ws/task_notifications.py` 提供了完整的 WebSocket 通知体系：

| 消息类型            | 用途          | 触发时机               |
| --------------- | ----------- | ------------------ |
| `task_created`  | 通知前端"任务已创建" | `execute_task()` 中 |
| `task_progress` | 推送进度百分比     | 每次工具调用后            |
| `task_complete` | 通知"任务完成"    | `_run_task()` 正常结束 |
| `task_failed`   | 通知"任务失败/取消" | 异常或取消时             |

这些通知通过 `connection_manager.broadcast()` 广播给所有 WebSocket 连接，前端可以用来显示进度条、弹窗等。

### （2）结果投递 `_deliver_result_to_session()`

通知只是告诉前端"状态变了"，真正把结果内容送到聊天界面的是 `_deliver_result_to_session()`：

```python
async def _deliver_result_to_session(self, task: SubagentTask) -> None:
    # 1. 根据任务状态构造消息内容
    if task.status == TaskStatus.COMPLETED:
        content = f"**子代理任务「{task.label}」已完成**\n\n{task.result}"
    elif task.status == TaskStatus.CANCELLED:
        content = f"**子代理任务「{task.label}」已取消**"
    else:
        content = f"**子代理任务「{task.label}」失败**: {task.error}"

    # 2. 通过 WebSocket 实时推送（复用前端已有的消息处理逻辑）
    await send_message_chunk(task.session_id, content)
    await send_message_complete(task.session_id, message_id=...)

    # 3. 持久化到数据库（刷新页面后仍能看到）
    db.add(Message(session_id=task.session_id, role="assistant", content=content))
    await db.commit()
```

关键设计：
- **复用 `send_message_chunk`**：前端本来就监听这个事件类型（正常聊天也用它），无需前端做任何改动
- **双写策略**：WebSocket 推送保证实时性，数据库写入保证持久性

### （3）完整数据流

```
子代理完成
    │
    ├─ notify_task_complete()           → WebSocket 广播（状态通知，前端可选监听）
    │
    ├─ _deliver_result_to_session()
    │     ├─ send_message_chunk()       → WebSocket 推送到聊天界面（用户实时看到）
    │     ├─ send_message_complete()    → 标记消息结束
    │     └─ db.add(Message(...))       → 持久化到数据库（刷新不丢失）
    │
    └─ finally: del running_tasks[id]   → 清理异步任务引用
```

## 10、多渠道局限与待改进

### （1）当前局限

`_deliver_result_to_session()` 使用 `send_message_chunk` 推送结果，这个函数只对 WebSocket 连接有效。也就是说：

| 用户来源            | 能否收到子代理结果 |
| --------------- | --------- |
| 前端网页（WebSocket） | 能，实时推送    |
| 飞书              | 不能        |
| Telegram        | 不能        |
| 其他渠道            | 不能        |

飞书/Telegram 用户通过渠道发送消息 → 主 Agent 调用 spawn → 用户收到"已启动"的回复 → 子代理完成后，结果推到了 WebSocket，渠道用户看不到。

### （2）为什么会这样？

`SubagentTask` 只存了 `session_id`，不知道这个会话来自哪个渠道。而 WebSocket 推送和渠道投递是两套完全不同的机制：

- **WebSocket**：`send_message_chunk(session_id, content)` → 通过 session_id 找到 WebSocket 连接
- **渠道投递**：`OutboundMessage(channel="feishu", chat_id="oc_xxx")` → 通过 ChannelManager 路由到对应渠道

### （3）改进方向

参考定时任务（CronExecutor）的做法——它已经正确实现了多渠道投递：

```python
# CronExecutor._deliver_to_channel()
channel_instance = self.channel_manager.get_channel(channel)
await channel_instance.send(OutboundMessage(channel=channel, chat_id=chat_id, content=message))
```

子代理要做到同样效果，需要：
1. `SubagentTask` 增加 `channel` 和 `chat_id` 字段
2. `SpawnTool` 创建任务时传入渠道信息
3. `_deliver_result_to_session()` 根据是否有渠道信息选择投递方式

## 11、关键设计决策

### （1）为什么子代理不共享主 Agent 的工具注册表？

每个子代理创建独立的工具注册表（`ToolRegistry`），而不是复用主 Agent 的。原因：
- **隔离性**：子代理的工具调用不影响主 Agent
- **权限控制**：子代理的工具权限更严格（无 spawn、无 memory）
- **线程安全**：避免并发访问同一个工具实例

### （2）为什么任务存在内存中而不是数据库？

`self.tasks` 是一个普通 dict，重启后丢失。这是有意为之：
- 子代理任务是临时的，不需要持久化
- 内存访问比数据库快得多
- 有 `cleanup_old_tasks()` 方法定期清理过期任务（默认 24 小时）

### （3）进度更新机制

进度不是精确计算的，而是简单递增：每执行一次工具调用，进度 +5，上限 90。最后完成时直接跳到 100。这是一种"模糊进度"——用户看到进度在动就知道任务还在运行。
